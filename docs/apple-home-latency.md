# Apple Home / Matterbridge 지연 점검

2026-09-28 저장소 코드 및 `matterbridge-hass 1.5.0` 소스 기준 분석이다.
설치된 HA, Virtual Layer, Matterbridge, matterbridge-hass 버전과 실제 로그를
확인하기 전에는 아래 후보를 실제 장애 원인으로 확정할 수 없다.

## 확인된 사례: Ventilator 29 → HA 20% 불일치

사용자 환경은 matterbridge-hass 1.5.0이며 Apple Home에서 29를 요청하면
HA에서는 지원 단계인 20%로 보정된다. 1.5.0의 `converters.ts`는 HA의
`percentage`를 Matter `percentCurrent`에만 반영한다. Apple Home이 쓴
`percentSetting`을 보정하는 경로는 없다. 또한 이미 HA가 20%인 상태에서
29를 요청하면 값이 동일해 새 상태 변경 이벤트가 없을 수 있다.
따라서 단순한 전송 지연보다 요청값/적용값 동기화 누락에 부합한다.

로컬의 인접 `matterbridge-hass` 저장소에 다음 수정을 적용했다.

- 수동 팬의 HA 풍속 갱신을 `percentSetting`에도 반영한다.
- percentage 서비스 완료 후 최신 HA 캐시로 설정값을 재확인하여 동일 값
  요청도 보정한다. 오래된 명령 완료는 더 최근 요청을 덮어쓰지 않는다.
- 자동 및 인식되지 않는 프리셋의 측정 속도를 수동 목표값으로 복사하지 않는다.
- 잘못된 값과 unavailable을 임의의 풍속으로 바꾸지 않는다.

실제 설치에는 수정된 **matterbridge-hass 플러그인** 빌드/설치와 재시작이
필요하다. Virtual Layer만 업데이트해서는 이 브리지 수정이 적용되지 않는다.
이 작업에서는 운영 인스턴스 설치 또는 Apple Home 실기기 검증을 하지 않았다.

검증: Virtual Layer의 light command latency/delayed commands/native templates
테스트 175개, 플러그인의 `module.test.ts`와 `module.matter.test.ts` 128개
통과. 후자는 실제 Matter 테스트 엔드포인트와 모의 HA 서비스를 사용해
설정값 보정, 동일 값 응답, 빠른 연속 요청, 서비스 실패, 자동/프리셋,
잘못된 값, unavailable/off를 확인한다. 전체 HA 테스트 및 Docker smoke는
이번 문서 변경에서 실행하지 않았다.

## 먼저 지연 구간 구분하기

하나의 문제가 있는 엔티티로 다음 두 동작을 각각 세 번 반복한다.
밝기/온도처럼 state 문자열이 그대로인 경우에는 해당 속성도 비교한다.

1. HA에서 원본 엔티티를 조작한다. 원본 → 가상 엔티티 → Apple Home의
   값이 바뀌는 순서와 시간을 기록한다.
2. Apple Home에서 조작한다. 플러그인의 명령 수신 → HA 서비스 실행 →
   원본 응답 → 가상 엔티티 갱신 → Apple Home 표시 시간을 기록한다.

| 늦어지는 구간 | 확인할 항목 |
| --- | --- |
| 원본 자체의 HA 값 | 물리 통신, 원본 통합의 보고/폴링, 서비스 응답 시간 |
| 원본은 즉시, 가상 엔티티만 지연 | 저장된 Jinja, 소스 목록, 액션의 delay/wait, 조명의 상태 유지 정책 |
| 가상 엔티티는 즉시, 플러그인 수신 지연 | HA WebSocket 연결/재연결, 플러그인 로그의 수신 시각 |
| 플러그인 수신은 즉시, Apple Home만 지연 | 속성 변환/누락, Matter 보고, 컨트롤러와 네트워크 경로 |

HA 개발자 도구의 `state_changed` 이벤트에서 원본과 가상 엔티티의
`time_fired`와 `new_state`를 비교한다. `last_changed`는 속성만 바뀌면
갱신되지 않으므로 밝기/온도 지연 측정에 사용하지 않는다. 플러그인의
`Received update event from Home Assistant` 로그와 대조한다. 다른 장비의
로그 시각을 비교할 때는 시계 차이도 확인한다. 이는 구간별 관측이며
Apple Home 표시까지의 자동화된 종단 측정은 아니다.

## 코드에서 확인된 동작과 개선 방향

- Virtual Layer는 설정된 소스의 상태 변경 이벤트와 Jinja 의존성을
  구독한다. 일반 소스 갱신에 고정 폴링 대기는 없다. `pull_interval`을
  무조건 1초로 줄이는 것은 이 경로를 고치지 못하고 렌더링 부하를 늘린다.
- 일반 명령은 원본 서비스 또는 설정된 액션이 완료된 뒤 로컬 명령 상태를
  적용한다. 액션에 긴 delay/wait가 있거나 원본 서비스가 느리면 HA 서비스
  반환도 늦어진다. 불필요한 대기는 제거하되, 필요한 순서와 실패 처리를
  유지한다. `optimistic: false`는 원본 확인을 따르는 의도된 동작이다.
- 기본 전달 액션을 쓰는 조명은 이미 즉시 목표 상태를 게시하며 소스 호출을
  기다리는 시간은 최대 50ms다(이벤트 루프 부하 및 전체 경로 시간 제외).
  느린 전구마다 최신 대기 명령만 남긴다. 커스텀 액션에는 이 조건이
  그대로 적용되지 않으므로 실제 저장된 액션을 확인한다.
- 단일 조명은 목표 확인 후 원본 추적을 재개한다. 응답 지연/재시도와
  transition은 미확인 목표의 유지 시간을 늘릴 수 있다. 여러 조명의
  그룹은 명령 후 목표 전원/밝기/색을 유지하도록 구현되어 있어 이후 멤버의
  개별 조작이 그룹에 그대로 반영되지 않을 수 있다. 이는 브리지 전송
  지연과 다르며 폴링 주기를 줄여도 해결되지 않는다. 개별 조작 반영이
  필요하면 별도 원본 추적 엔티티 또는 그룹 정책 변경이 필요하다.
- 플러그인 1.5.0은 꺼진 light/fan의 **속성** 갱신을 건너뛴다. 전원 상태
  갱신과 구분해야 한다. 꺼진 팬의 속도나 꺼진 조명의 밝기가 이전 값이면
  무조건 네트워크 지연으로 판단하지 않는다. 해당 동작을 바꾸려면 설치된
  플러그인의 변환 정책을 확인하고 플러그인 쪽에서 수정해야 한다.
- 같은 Matter Device로 묶인 엔티티의 unavailable 이벤트는 플러그인에서
  Device 전체 reachable을 바꿀 수 있다. 문제가 되는 Device에 선택된
  엔티티와 unavailable 이벤트를 확인한다. 브리지 선택에는 필요한 제어 및
  측정 엔티티만 포함하고 info/debug/usage 진단 엔티티의 불필요한 노출을
  제외한다. 배터리는 부모 Device 관계를 유지한다. 노출 축소가 실제
  지연을 줄이는지는 전후 측정으로 판단한다.

단순 지연 점검을 위해 재페어링하거나 모든 재시도를 끄지 않는다. 먼저
문제 구간을 확인한 뒤 해당 설정 하나만 변경하고 동일한 동작으로 비교한다.
이 문서 작성 중 실행 중인 HA/브리지 설정은 변경하지 않았다.
